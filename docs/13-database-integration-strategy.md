## 1. Integration Architecture

### 1.1 Partners and Data Flow

FoodSafe exchanges data with three external government agencies. Data flows in both directions (inbound and outbound) depending on the data type:

| Partner | Vietnamese Name | Direction | Data Types |
|---------|----------------|-----------|------------|
| **Bộ Y tế** | Ministry of Health | Outbound + Inbound | FoodPoisoning, Alerts, InspectionResults |
| **Sở Nông nghiệp** | Dept. of Agriculture | Outbound | Products, Businesses |
| **Sở Công thương** | Dept. of Industry and Trade | Outbound + Inbound | Alerts, News, Licenses |

**Outbound**: FoodSafe pushes data to the partner system when significant events occur (e.g., a food poisoning incident is verified, an alert is published). Hangfire background jobs handle the delivery and retry.

**Inbound**: Partner systems push data to FoodSafe via a dedicated inbound endpoint. FoodSafe validates, deduplicates (idempotency), and creates/updates records. All inbound calls are logged to `data_sharing_histories` before processing.

### 1.2 api_specs Table Design

`api_specs` stores the configuration for each integration endpoint. One row per partner system:

```sql
CREATE TABLE api_specs (
    id                      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name                    VARCHAR(200) NOT NULL,   -- e.g., 'Bộ Y tế - NĐTP API'
    partner_code            VARCHAR(50) NOT NULL,    -- 'MOH' | 'DOA' | 'DOIT'
    direction               VARCHAR(10) NOT NULL,    -- 'Outbound' | 'Inbound' | 'Both'
    base_url                VARCHAR(500),            -- NULL for inbound-only specs
    auth_type               VARCHAR(30) NOT NULL,    -- 'ApiKey' | 'OAuth2' | 'BasicAuth' | 'None'
    auth_config_encrypted   TEXT,                    -- AES-256 encrypted JSON blob
    supported_data_types    VARCHAR(500),            -- comma-separated list
    timeout_seconds         INTEGER NOT NULL DEFAULT 30,
    is_active               BOOLEAN NOT NULL DEFAULT TRUE,
    contact_person          VARCHAR(200),
    contact_email           VARCHAR(200),
    api_version             VARCHAR(20),
    notes                   TEXT,
    -- ABP audit
    is_deleted              BOOLEAN NOT NULL DEFAULT FALSE,
    creation_time           TIMESTAMPTZ NOT NULL DEFAULT now(),
    creator_id              UUID,
    last_modification_time  TIMESTAMPTZ,
    last_modifier_id        UUID
);
```

**Purpose**: `api_specs` acts as a registry of integration configurations. Each row is referenced by `data_sharing_histories.api_spec_id`, creating a clear link between a specific API configuration and its usage history. When credentials change (key rotation), only the `auth_config_encrypted` field is updated — all historical records still reference the same `api_spec_id`.

### 1.3 data_sharing_histories Table Design

`data_sharing_histories` is the audit trail for every integration call. It is an **insert-only** table (no hard deletes; no record updates except for retry lifecycle fields).

**Lifecycle states:**
```
Sending → Success       (happy path)
Sending → Failed → (retry) → Sending → ...
Failed (4 retries) → ManualReview
Inbound: Received → Processed | Rejected | Duplicate
```

**Relationship to api_specs:**
- `data_sharing_histories.api_spec_id` → `api_specs.id` (mandatory FK)
- Allows querying all calls for a specific partner: `WHERE api_spec_id = $mohApiSpecId`
- Allows querying all calls for a specific data type: `WHERE data_type = 'FoodPoisoning'`

## 2. Idempotency

### 2.1 The Problem

When FoodSafe receives inbound data from a partner system, network failures or retries at the partner side may cause the same data to be delivered more than once. Without idempotency controls:

- Duplicate food poisoning cases could be created for the same incident
- Duplicate businesses could be registered from the same MOH push
- Duplicate alerts could be published

Because FoodSafe's domain objects have UNIQUE constraints on business-identifying fields (e.g., `tax_code` on `businesses`, `registration_number` on `product_registrations`), some duplicates would fail at the DB level — but not all. A poisoning case with slightly different victim data but same source would pass all constraints and create a ghost record.

### 2.2 Solution: idempotency_key for Inbound Requests

Every inbound API endpoint requires the caller to supply an `Idempotency-Key` HTTP header. This key is:
- Generated by the partner system per logical operation (not per HTTP request)
- A stable string that identifies the business event: e.g., `moh-poisoning-case-{partnerCaseId}-{timestamp}`
- Stored in `data_sharing_histories.idempotency_key`

**Processing flow:**
```
1. Inbound request arrives at /api/integration/inbound/{data-type}
2. Extract Idempotency-Key header → error 400 if missing
3. Query: SELECT id, status FROM data_sharing_histories WHERE idempotency_key = $key
4a. If found AND status = 'Processed' → return 200 OK with cached response (no reprocessing)
4b. If found AND status = 'Processing' → return 409 Conflict (concurrent duplicate)
4c. If not found → INSERT record with status = 'Processing', begin processing
5. Process the inbound data (create/update domain records)
6. UPDATE data_sharing_histories SET status = 'Processed', completed_at = now(), response_payload = ...
7. Return 200 OK

On step 5 failure:
6. UPDATE data_sharing_histories SET status = 'Rejected', error_message = ...
7. Return 422 Unprocessable Entity
```

**UNIQUE index on idempotency_key:**
```sql
CREATE UNIQUE INDEX idx_data_sharing_idempotency ON data_sharing_histories (idempotency_key)
    WHERE idempotency_key IS NOT NULL;
```

This ensures that even if two concurrent requests arrive simultaneously with the same key, the DB constraint rejects the second INSERT, preventing race conditions.

### 2.3 Outbound Correlation

For outbound calls, FoodSafe generates a correlation ID and includes it in the API request (as `X-FoodSafe-Correlation-Id` header or in the payload). This allows the partner system to deduplicate on their side and allows FoodSafe to correlate a response/callback to the original request.

The correlation ID is stored in `data_sharing_histories.external_entity_id` (or a dedicated `correlation_id` column if a partner system returns their own ID in the response — store that as `external_entity_id`).

## 3. Retry Strategy

### 3.1 Hangfire Background Jobs

Outbound API calls are not made synchronously during the user's HTTP request. Instead:

1. The AppService publishes a domain event (e.g., `AlertPublishedEvent`)
2. A domain event handler inserts a `data_sharing_histories` record with `status = Sending`
3. A Hangfire job picks up the record and makes the actual HTTP call
4. The Hangfire job updates the record's `status`, `http_status_code`, `response_payload`, `completed_at`

This decouples the user-facing operation from the external call latency and ensures retries are managed by Hangfire's reliable scheduler.

**Job registration:**
```csharp
// Recurring job to process pending outbound records
RecurringJob.AddOrUpdate<DataSharingOutboundJob>(
    "process-outbound-integration",
    job => job.ProcessPendingAsync(),
    Cron.Minutely);

// Recurring job to retry failed records
RecurringJob.AddOrUpdate<DataSharingRetryJob>(
    "retry-failed-integration",
    job => job.RetryDueAsync(),
    Cron.MinuteInterval(5));
```

### 3.2 next_retry_at and retry_count

The retry schedule uses exponential backoff with jitter:

| Attempt | Wait before retry | next_retry_at formula |
|---------|------------------|----------------------|
| 1st failure | 5 minutes | `now() + interval '5 minutes'` |
| 2nd failure | 30 minutes | `now() + interval '30 minutes'` |
| 3rd failure | 2 hours | `now() + interval '2 hours'` |
| 4th failure | 12 hours | `now() + interval '12 hours'` |
| 5th failure | ManualReview | No further retry |

Jitter: add ±20% random variance to each wait duration to prevent thundering herd when many records fail simultaneously.

Implementation:
```csharp
private static TimeSpan GetRetryDelay(int retryCount) => retryCount switch
{
    0 => TimeSpan.FromMinutes(5),
    1 => TimeSpan.FromMinutes(30),
    2 => TimeSpan.FromHours(2),
    3 => TimeSpan.FromHours(12),
    _ => TimeSpan.MaxValue  // triggers ManualReview
};
```

The `DataSharingRetryJob` queries:
```sql
SELECT * FROM data_sharing_histories
WHERE status = 'Failed'
  AND next_retry_at <= now()
  AND retry_count < 4
ORDER BY next_retry_at
LIMIT 50;  -- process in batches to avoid Hangfire job timeout
```

### 3.3 Dead Letter — ManualReview Status

When `retry_count >= 4` and the attempt still fails, the record transitions to `ManualReview`:

- `status = 'ManualReview'`
- `next_retry_at = NULL`
- No further automatic retry

**ManualReview handling in the UI:**
- A badge in the `DataIntegration` module shows the count of `ManualReview` records
- ProvinceAdmin can view the full error history and choose to:
  - **Force retry**: resets `status = Failed`, `retry_count = 0`, `next_retry_at = now()` (immediate pickup)
  - **Mark as resolved**: sets `status = ManuallyResolved` with a resolution note (used when the partner system confirms they received the data via an alternate channel)
  - **Discard**: sets `status = Discarded` (data will not be resent)

All ManualReview actions are logged via ABP AuditLog since they modify the `data_sharing_histories` record.

## 4. Payload Storage Strategy

### 4.1 Small Payloads (≤ 1 MB)

Stored directly in `request_payload` and `response_payload` TEXT columns. This covers the vast majority of integration calls (alerts, poisoning case summaries, inspection result summaries).

**Advantages:**
- No external dependency for payload retrieval
- Atomic with the DB transaction
- Fast querying and display in the UI

**Format**: JSON string. No compression for payloads ≤ 1 MB.

### 4.2 Large Payloads (> 1 MB)

Stored in MinIO under the bucket `integration-payloads`:

```
integration-payloads/
  outbound/
    {year}/
      {month}/
        {data_sharing_history_id}-request.json
        {data_sharing_history_id}-response.json
  inbound/
    {year}/
      {month}/
        {data_sharing_history_id}-request.json
```

The `data_sharing_histories` row stores:
- `request_payload = NULL`
- `response_payload = NULL`
- `payload_storage_path = 'outbound/2026/07/{id}-request.json'`

To retrieve the payload, the AppService generates a presigned MinIO URL (15-minute expiry) and returns it to the admin UI.

**Threshold**: 1 MB is the recommended threshold. A batch export of 500 businesses with full product lists may exceed this.

### 4.3 Checksum

`payload_checksum` stores the SHA-256 hex digest of `request_payload` (or of the MinIO object content if large). Computed before insertion:

```csharp
var checksum = Convert.ToHexString(
    SHA256.HashData(Encoding.UTF8.GetBytes(requestPayload))
).ToLowerInvariant();
```

**Purpose:**
1. Tamper detection: if the DB row's payload is ever modified (should not happen due to REVOKE), the checksum mismatch is detectable
2. Deduplication: if the same payload checksum appears multiple times for the same `api_spec_id` and `data_type` within a short window, it may indicate a configuration issue causing repeated sends

## 5. Data Type Mapping

The 7 data types shared with external systems and their source tables in FoodSafe:

| DataType | Source Tables | Key Fields Shared | Target Entity (Partner) |
|----------|--------------|------------------|------------------------|
| **Alert** | `atp_alerts` | `title`, `content`, `alert_level`, `affected_products`, `published_at` | MOH Alert Registry, DOIT News Portal |
| **InspectionResult** | `inspection_results`, `inspection_violations` | `business_id` (+ partner entity ref), `inspection_date`, `result_summary`, `violation_count`, `has_violation` | MOH Inspection Database |
| **FoodPoisoning** | `food_poisoning_cases`, `food_poisoning_incidents` | `occurrence_date`, `victim_count`, `hospitalized_count`, `death_count`, `suspected_cause`, `location` | MOH NĐTP Surveillance System |
| **License** | `product_registrations`, `eligibility_certificates`, `cfs_certificates`, `export_food_certificates` | `license_type`, `license_number`, `business_id`, `issue_date`, `expiry_date`, `status` | DOIT License Registry |
| **Product** | `products`, `product_registrations`, `self_declarations` | `product_name`, `product_group`, `manufacturer`, `registration_number`, `declaration_number` | DOA Product Database |
| **News** | `atp_news` | `title`, `content`, `published_at`, `category` | DOIT News Portal |
| **Business** | `businesses`, `business_handlers` (PII filtered) | `name`, `tax_code`, `business_type`, `address`, `status` | DOA Business Registry, MOH Business Database |

**PII filtering for outbound Business data**: `representative_id_card` and `id_card_number` from `business_handlers` are **never included** in outbound payloads to external systems. Only publicly shareable fields are included.

## 6. Security

### 6.1 API Credentials

Credentials for external APIs are stored in `api_specs.auth_config_encrypted` as an AES-256-GCM encrypted JSON blob. The structure of the decrypted JSON depends on `auth_type`:

```json
// ApiKey
{ "header_name": "X-API-Key", "api_key": "..." }

// OAuth2
{ "token_url": "...", "client_id": "...", "client_secret": "...", "scope": "..." }

// BasicAuth
{ "username": "...", "password": "..." }
```

**Key management:**
- Encryption key is stored in environment variable `FOODSAFE__DATAPROTECTION__KEY` (never in appsettings committed to git)
- ASP.NET Core Data Protection API is used for encryption/decryption
- Key rotation: when the key is rotated, all `auth_config_encrypted` values must be re-encrypted. A migration job (`ApiSpecKeyRotationJob`) handles this.
- The decrypted credential is held in memory only for the duration of the outbound HTTP call; it is never logged, never returned in API responses.

### 6.2 Inbound API Security

Inbound endpoints receive data from external partners. Security controls:

| Control | Implementation |
|---------|---------------|
| **Authentication** | Partners authenticate with an API key sent in `Authorization: Bearer {key}` header. Keys are stored hashed in `api_specs` for inbound direction. |
| **IP allowlisting** | nginx/reverse proxy allows inbound integration traffic only from whitelisted partner IP ranges |
| **HTTPS only** | All inbound and outbound calls use TLS 1.2+ |
| **Rate limiting** | 100 requests per minute per partner API key (nginx `limit_req` module) |
| **Payload size limit** | 10 MB max per request (nginx `client_max_body_size`) |
| **Input validation** | All inbound payloads are validated against strict JSON schemas before processing |

### 6.3 Audit Trail

`data_sharing_histories` is the primary audit trail for all integration operations. Because it is insert-only (application-level; see Section 12 of doc 12 for DB-level REVOKE), it provides an immutable record of every integration event.

**Non-repudiation for disputes:**
- FoodSafe can prove it sent a specific alert to Bộ Y tế at a specific time with a specific payload, by presenting the `data_sharing_histories` record + the checksum of the payload
- FoodSafe can prove it received a specific inbound request and either processed or rejected it, with the full request payload and the timestamp

## 7. Thông tư 31/2026/TT-BCT Compliance

Thông tư 31/2026/TT-BCT governs data sharing between government agencies in Vietnam's food safety management ecosystem. Key compliance requirements and how FoodSafe meets them:

### 7.1 Data Exchange Standards

| TT31 Requirement | FoodSafe Implementation |
|-----------------|------------------------|
| Use standard data formats (JSON or XML) | FoodSafe uses JSON for all API payloads; XML supported as a serialization option for legacy partners |
| Include data source identifier in every payload | `provider_code` field in outbound payloads identifies `FoodSafe-QuangNinh` |
| Include timestamp of data generation | `generated_at` field in all outbound payloads; stored in `data_sharing_histories.sent_at` |
| Include data version number | `data_version` field increments when schema changes; `api_specs.api_version` tracks the contract version |
| Encrypt sensitive data in transit | TLS 1.2+ mandatory for all endpoints |

### 7.2 Logging and Accountability

| TT31 Requirement | FoodSafe Implementation |
|-----------------|------------------------|
| Log all data exchange operations | `data_sharing_histories` records every call with full metadata |
| Retain integration logs for minimum 2 years | Retention policy: 2 years, enforced by Hangfire cleanup job |
| Provide lookup mechanism for exchange history | `GET /api/data-integration/histories` endpoint (ProvinceAdmin+) with date range and partner filters |
| Report disputes within specified timeframes | `ManualReview` status enables staff to identify failed exchanges and resolve within required timeframes |

### 7.3 Data Accuracy and Completeness

| TT31 Requirement | FoodSafe Implementation |
|-----------------|------------------------|
| Validate data before transmission | Outbound domain event handler validates required fields before inserting `Sending` record |
| Deduplicate inbound data | `idempotency_key` UNIQUE constraint prevents duplicate processing |
| Notify partner of rejected data | On validation failure, inbound endpoint returns 422 with structured error details; this is logged in `data_sharing_histories` with `status = Rejected` and `error_message` |
| Maintain referential integrity across systems | `external_entity_id` field stores partner system's ID for cross-system entity correlation |

### 7.4 API Specification Publication

| TT31 Requirement | FoodSafe Implementation |
|-----------------|------------------------|
| Publish API specification for consumed endpoints | `api_specs` table contains spec URL/documentation link per partner |
| Publish API specification for provided endpoints | FoodSafe's inbound API is documented in `06-api-contracts.md` Section F; OpenAPI spec auto-generated by Swashbuckle |
| Version management for breaking changes | Endpoint versioning via URL path (`/api/v1/integration/...`); `api_specs.api_version` tracks consumed version |

### 7.5 Data Sovereignty and Residency

All data exchanged under TT31 remains within Vietnamese government infrastructure:
- FoodSafe is deployed on-premises within Quảng Ninh province government data center
- Partner systems are also on-premises Vietnamese government systems
- No data transits through foreign infrastructure
- MinIO for payload storage is self-hosted (not AWS S3) — data residency is guaranteed
## v2.3 retry-history correction

`data_sharing_histories` is the logical envelope and current delivery/scheduling
state. The initial exchange and every retry insert one immutable
`data_sharing_attempts` row. Attempt rows preserve endpoint, request/response,
checksums, timing, outcome, and error; retry processing must never overwrite an
earlier attempt. Partner-scoped idempotency/correlation and immutable API-spec
revisioning remain open contract questions and were not added without source
authority.
